# Task lifecycle investigation and repair plan

The baseline is Pet-Zoo-Code commit `44b3464fb`, reviewed on November 26, 2026.

Two cross-host races can corrupt task history. An old child completion can clear a newer handoff, and a routine message save can restore links that another host removed. The same investigation reproduced a presenter ownership race and two paths that drop queued messages. A separate presenter failure can leave a task waiting for a tool result that the presenter will never produce. Repair persisted ownership first. Queue delivery and presenter ownership can use separate patches.

The existing models still pass their required checks. They also require the known failures to stay reproducible until a patch replaces each witness with a regression invariant. This report links those witnesses to current production code and gives the evidence required to close each finding. [Lifecycle models](task-lifecycle-model.md) · [Remediation register](task-lifecycle-remediation-blocks.md)

## Implementation and verification

The patch checks the awaited child, pending action, and attempt generation against the locked task record. A late completion may leave its own child record complete. The parent retains its newer handoff and both of its transcripts. If the child committed and publication failed, startup can replay the parent result while that handoff still owns it. The result uses the recorded tool call when available, and older records without an unambiguous call can use a text result. Routine saves preserve persisted lineage. Replay of an active-child repair checks the attempt generation recorded in the journal.

The presenter checks its owner before advancing, publishing a result, or releasing dispatch. A known failure to read tool policy produces a matching error result. An incomplete turn with an uncertain execution outcome stops and preserves any results already available. An ask holds a queued entry by ID until it accepts the answer. Replacement releases the old claim before selecting another entry. Lifecycle feedback keeps the claim until the history write succeeds.

- macOS on Node `22.23.4` ran the focused regressions, repository test suite, type checks, changed-file lint, and both model commands. All 13 repository test tasks passed. The extension package passed 16,033 tests and skipped 39. The shared-store model checked 1,288 states, the presenter model checked 7,968, and the queue model checked 176. The original failure paths remain as injected unsafe variants.
- VS Code `1.100.0` on macOS passed both restart phases with provider replay. Three subtask smoke tests also passed for persisted completion, cancel and resume, and abandonment.
- Ubuntu `24.04` on Node `22.23.4` passed three real-filesystem smoke tests and the three affected model scripts. The smoke tests used the production store with a VS Code configuration stub.
- Windows, live provider accounts, and an interleaving across two live VS Code windows remain unverified. The two-store tests exercise shared files and advisory locks. Detecting which host owns a live child during startup still requires a cross-host lease. A presenter reset also cannot undo a side effect that a tool already started.

## 1. Findings and production evidence

### An old completion can clear a newer handoff

**Impact.** The parent returns to `active` and records child A as the completing child. Child B stays active and still links to the parent, but the parent no longer awaits B. A delayed completion can therefore strand a valid newer child. The parent still lists both children because the merge unions `childIds`. That list does not prove which child owns the handoff.

**Reproduction.** Two production `TaskHistoryStore` instances shared a temporary directory and used the real file locks and writes. Both stores initialized before the test seeded the live handoff, so startup repair did not alter the fixture. A prepared completion for child A. B interrupted A. A committed the child record. A test barrier then let B write the handoff to child B before A wrote the parent record. Reading the files confirmed that A cleared `awaitingChildId`, set `completedByChildId` to A, and left B active. The shared-store model reaches this outcome in 14 actions. [Store model](../../scripts/check-task-store-concurrency.ts#L700) · [Pair write](../../src/core/task-persistence/TaskHistoryStore.ts#L939)

**Cause.** The store runs pair updaters against host-local cache entries. Each file write takes its own advisory lock. At merge time, the store checks whether the status transition is legal. Both old and new handoffs use the same status vocabulary, so `delegated → active` can succeed even when the disk record awaits a different child. The continuation check later in the provider can suppress a stale restart, but it runs after the authoritative write. [Disk merge](../../src/core/task-persistence/taskStoreConcurrency.ts#L24) · [Completion](../../src/core/webview/ClineProvider.ts#L5080) · [Continuation check](../../src/core/webview/ClineProvider.ts#L5158)

**Related transcript risk.** Completion saves the parent's UI result and API tool result before the task-history pair write. A lock-time check in the parent history write would therefore leave those earlier results outside the check. The provider also finds the latest `new_task` call by scanning the API history. When ownership changes, the old result can reach the transcript or be associated with the wrong call. The transcript risk follows from code order. The two-store reproduction verified the history-file overwrite. [UI result write](../../src/core/webview/ClineProvider.ts#L4971) · [API result write](../../src/core/webview/ClineProvider.ts#L5063)

### A message save can restore detached lineage

**Impact.** An abandoned child can regain `parentTaskId` and `rootTaskId` while remaining `interrupted`. The parent is active and no longer awaits that child. Different readers can then disagree about whether the task is standalone.

**Reproduction.** With two production stores and real files, A held a live snapshot of child A. B interrupted and abandoned the child. After A refreshed its cache, A saved metadata from the stale snapshot with the current `interrupted` status and a new token count. Disk kept the new count and status and restored both old links. The shared-store model reproduces the same failure through its 11-action witness. [Stale-save scenario](../../scripts/check-task-store-concurrency.ts#L726) · [Abandonment](../../src/core/webview/ClineProvider.ts#L5232)

**Cause.** `Task.saveClineMessages()` builds a full history item from live task fields and copies the cached status onto it. The new cache correctly shows the child as detached. This makes the old links look like deliberate edits when the store calculates the delta. The disk merge applies those edits. Closing a child in the initiating window does not stop another window from saving its own live snapshot. [Message save](../../src/core/task/Task.ts#L1842) · [Delta calculation](../../src/core/task-persistence/taskStoreConcurrency.ts#L16)

### A stale presenter can release a newer presenter's lock

**Impact.** A third presentation pass can enter while the newer pass is still active. Two passes can then work on the same turn state. Duplicate tool execution or misplaced results are possible consequences. The reproduction verified the loss of ownership at the presenter boundary.

**Reproduction.** The real presenter ran against a task double with two separately blocked calls. The test used the same dispatch reset that the request loop uses. After the second pass acquired the lock, ending the first pass changed the shared dispatch state to `IDLE` while the second pass was still blocked. The model records the same seven-action failure. [Presenter release](../../src/core/assistant-message/presentAssistantMessage.ts#L86) · [Request reset](../../src/core/task/Task.ts#L4265) · [Tool-turn model](../../scripts/check-tool-turn-continuation.ts#L461)

### A presenter failure can leave a tool turn waiting

**Impact.** If a tool block has no matching result, the request loop can stay in its readiness wait until cancellation or abandonment.

**Reproduction.** A test double rejected `getTaskMode()` before the tool handler ran. The real presenter rejected and released the lock, with no result and no ready signal. The readiness check requires a matching result for each finalized call. The request loop has no terminal presenter-failure condition. The three-action model witness shows the resulting stuck state. The presenter test verified the rejection and missing result. The model and source establish the indefinite wait. The existing positive regression covers a presenter failure after the matching results already exist. [Presenter wrapper](../../src/core/task/Task.ts#L587) · [Readiness check](../../src/core/task/Task.ts#L647) · [Request wait](../../src/core/task/Task.ts#L5230) · [Existing positive test](../../src/core/task/__tests__/Task.spec.ts#L1140)

### A drain can drop a queued message before an ask starts

**Impact.** The queue entry disappears, and the next ask can erase the only pending copy. Text, images, and mention segments travel through that same response slot.

**Reproduction.** Production Task and queue methods ran with controlled timers and stubbed UI and persistence. Both direct `processQueuedMessages()` and a drain released by `commitEdit()` removed the entry and deferred submission. When submission ran before an ask was waiting, it populated the response slot. The next follow-up ask reset the slot, and the entry was absent from the queue. An explicit answer then resolved the ask. The model reproduces the drop in four actions. Its injected check for ask presence alone also fails when a second message overwrites a full slot. [Task drain](../../src/core/task/Task.ts#L6611) · [Response slot](../../src/core/task/Task.ts#L2468) · [Queue model](../../scripts/check-queue-ask-landing.ts#L241)

## 2. Repair order and acceptance criteria

### 1. Protect parent ownership and result delivery

1. Add deterministic two-store regression cases to the existing real-lock suite. Cover first delegation, re-delegation, completion, and abandonment. In each case, prepare a write in A, let B change the awaited child, then run A's real disk merge. Include valid writes and the existing recovery case where an active parent still names the expected child. [Real-lock suite](../../src/core/task-persistence/__tests__/TaskHistoryStore.realConcurrency.spec.ts) · [Ownership model](task-lifecycle-persisted-ownership-model.md#life-blk-p1-001--lock-time-ownership-check-gap-001)
2. Give each parent lifecycle mutation an expected awaited-child value, including an explicit expectation that no child is awaited. Compare that value against the authoritative record inside the parent file lock. Verify pending action identity under the same lock when the operation consumes an approval. Use a typed conflict outcome. Reject missing or invalid records and preserve newer pending actions. The existing disk compare-and-clear operation provides a pattern for validating the locked record. [Shared reducers](../../src/core/task-persistence/taskLifecycle.ts) · [Compare-and-clear](../../src/core/task-persistence/TaskHistoryStore.ts#L1026)
3. Make the same authorization cover result visibility in both transcripts. Stage each completion with a stable delivery identity. Associate the result with the accepted delegation and its tool call. Record authorization durably with the parent transition. Serialize transcript publication and competing ownership changes, or keep staged results invisible to readers until the accepted transition is recoverable. A preflight refresh or a guard added only to the final metadata write leaves a race. Test two children with equal result text and changes to the latest `new_task` call.
4. Keep the child-first roll-forward rule from ADR-0005. If a newer handoff wins, retain the child's committed state and publish no result for it to the parent. If an I/O failure leaves the same handoff on disk, retry the authorized parent update. On restart, apply the same ownership rules during repair. Inject failures before child commit, between the child and parent commits, and between each transcript publication step. Verify a repeated repair neither adds a second result nor clears a newer handoff. [Roll-forward decision](adr/0005-pair-write-roll-forward.md) · [Recovery blocks](task-lifecycle-remediation-blocks.md#p2-durable-operation-and-crash-recovery)
5. Add attempt generation in the child file to cover a late completion from a previous attempt of the **same** child ID. Keep that comparison distinct from the parent ownership check. Define old-record defaults and cover interruption, resumption, and a late completion under the child lock. [Attempt generation decision](adr/0003-attempt-generation.md)

Close the cross-host completion finding when the old writer can change neither the newer handoff nor either parent transcript. Promote the stale-completion witness to an enforced model invariant after the production regression passes. Keep expected rejection, child-first partial commits, and valid completion reachable in the model.

### 2. Limit message saves to metadata fields

Split record creation from routine metadata updates. Initial creation can set lifecycle fields. Updates for an existing task should accept a typed allowlist of message-derived fields, such as usage, timestamp, and task summary. Use typed lifecycle operations for status, lineage, awaited-child fields, completion fields, and pending actions. Audit existing full-record `updateTaskHistory()` callers by purpose so legitimate status and profile operations retain their behavior. Use the disk record to distinguish an existing task from a missing or deleted one. [Field ownership specification](task-lifecycle-persisted-ownership-model.md#life-blk-p1-002--lifecycle-owned-fields-versus-metadata-writes-gap-002) · [Message metadata caller](../../src/core/task/Task.ts#L1860)

Close the finding when the two-store abandonment replay preserves detached lineage, keeps legitimate metadata changes, and preserves a peer's unrelated fields. Test both link-present and link-absent snapshots, successful creation of a new task, and a late save after deletion. Promote monotonic detachment to an invariant. This patch can ship separately from transcript publication because the metadata writer can enforce its own field ownership.

### 3. Bind presentation and failure to the request that owns them

1. Give each presentation pass an owner tied to the request generation. Release dispatch state, drain pending work, and update readiness only if the current request still owns the pass. Check ownership again after asynchronous work and before writing a result or advancing the index. A token check in `finally` alone leaves those other effects exposed.
2. Give the request loop a terminal outcome for a failed presentation. When the same request still owns the call and the tool has a definite failure, settle that call with one matching error result. For an unknown side-effect outcome, stop at an explicit error or retry decision. Preserve prior results and avoid automatic execution of the same operation. Cancellation or replacement must win over a late failure. This also preserves the existing stream replay guard. [Tool dispatch](../../src/core/assistant-message/dispatchToolUse.ts) · [Request retry guard](../../src/core/task/Task.ts#L4856)
3. Use deferred promises to cover old-pass release after reset, late result writes, failures before and after a result, multiple calls, and cancellation. Test a positive continuation with all calls paired. Promote the ownership and terminal-failure invariants separately so a passing model still requires valid work to complete. [Presenter tests](../../src/core/assistant-message/__tests__/presentAssistantMessage.spec.ts) · [Tool-turn model](../../scripts/check-tool-turn-continuation.ts)

### 4. Retain queued messages until an eligible consumer accepts them

Replace the eager removal in the two Task drain paths with claim-and-acknowledge behavior. Retain the same message ID, payload, and order when an ask is absent, already answered, protected, or superseded. Let the existing ask consumer apply the command and tool approval rules. Bind any deferred delivery to the exact pending ask and release its claim when ownership changes. The run-state ask helpers have no production callers on the reviewed commit, so use the live ask lifecycle to establish that identity. For lifecycle feedback, acknowledge only after the existing history write succeeds. Make edit completion wake a waiting consumer. [Queue service](../../src/core/message-queue/MessageQueueService.ts) · [Ask lifecycle helpers](../../src/core/task/Task.ts#L3612) · [Ask drain tests](../../src/core/task/__tests__/ask-queued-message-drain.spec.ts)

Close the finding when every message stays queued, claimed by one consumer, or acknowledged exactly once. Cover direct and edit-blocked drains, two messages competing for one slot, same-text messages with different IDs, a manual reply arriving first, protected asks, command output, failed persistence, and cancellation. Use the real claim logic in the bounded model where possible. Keep task-disposal and restart durability as the separate product contract in `LIFE-BLK-P5-031`. [Queue remediation blocks](task-lifecycle-remediation-blocks.md#p5-tool-owned-task-state-and-queueing)

### Local VS Code launch finding

The first macOS launch inherited `ELECTRON_RUN_AS_NODE` and treated the workspace path as a JavaScript module. It exited before creating the first phase result. The same build passed after the launch environment excluded that variable, `NODE_OPTIONS`, and inherited `VSCODE_*` variables, with the VS Code version set explicitly. The restart coordinator copies its incoming environment. A small harness patch can sanitize parent-host variables at that boundary and report the child exit when a phase result is missing. This launcher issue is separate from persistence correctness. [Restart coordinator](../../apps/vscode-e2e/src/restart/vscodeCoordinator.ts#L44)

### Release evidence

Require three kinds of evidence for each repair. First, a deterministic production regression must fail on the old behavior and pass with the repair. Second, update the relevant model and retain a reachable valid path. Third, link the CI or local host evidence for the OS and workflow that the change affects. The highest-priority release gate is that a late result preserves the newer handoff and both parent histories.
